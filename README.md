# 2Money — backend

Express + PostgreSQL API for the 2Money family finance tracker. Google
sign-in is verified via Firebase Admin (`firebase-admin`); all business data
(accounts, categories, transactions, recurring templates, budgets, users)
lives in PostgreSQL — there is no Firestore involved anywhere.

## Stack

- **Express 5**, plain REST routers per resource (`src/routers/*.js`) — no RPC dispatcher.
- **PostgreSQL 17** (see `docker-compose.yml`), migrated with `node-pg-migrate` (`migrations/`).
- **firebase-admin**, ID-token verification only (`src/middleware/auth.js`) — Firebase Auth is the identity provider, this app owns authorization itself via the `users` table.
- All primary keys are **UUIDv7** (`src/util/uuid.js`, the `uuid` npm package — Postgres 17 has no built-in `uuidv7()`), generated by the caller (server for admin actions, the frontend client for everything else) so an offline client can assign a record's id before it ever reaches the server.

## Setup

```bash
docker compose up -d      # Postgres on the port in .env (POSTGRES_PORT / exposed as 5433 by default)
npm install
npm run migrate:up
npm run dev                # nodemon + cluster (one worker per CPU), ports PORT / PORT_ADMIN from .env
```

`.env` needs `POSTGRES_*`, `PORT`/`PORT_ADMIN`, and a Firebase service account (`GOOGLE_*` — from Firebase Console → Project settings → Service accounts → Generate new private key).

## Authorization model

There is no separate allowlist collection/table. `users` IS the allowlist:

1. First ever Google sign-in (the `users` table is empty) auto-creates that person as `role: 'owner'`.
2. Every sign-in after that only succeeds if the signing-in email already has a row in `users` — either because they signed in before, or because an owner pre-provisioned them via `POST /api/admin/users`.
3. A `role: 'owner'` can manage other users (`GET/POST/PATCH /api/admin/users`); everyone else is `role: 'member'`.

See `src/middleware/auth.js`.

## Offline-first sync contract

Every "syncable" resource (`accounts`, `categories`, `transactions`,
`recurring-templates`, `budgets`) follows the same shape, so a client can
work fully offline and reconcile later:

- `id` is always client-generated (UUIDv7) and sent by the client.
- `POST /api/<resource>` is an **idempotent upsert** keyed by `id` (`ON CONFLICT (id) DO UPDATE`) — replaying a queued offline write is always safe.
- `DELETE /api/<resource>/:id` is a **soft delete** (`deleted_at`), not a hard delete — so a client that was offline finds out about it instead of never hearing back.
- `GET /api/<resource>?since=<epoch-ms>` returns only what changed since that cursor, **including tombstones** (`deletedAt` set) — the response is `{ items, syncedAt }`, and `syncedAt` becomes the next `since`.
- `GET /api/accounts?scope=all` / `GET /api/transactions?scope=all` return the whole family's active records (this app's trust model is full financial transparency between family members, not per-member isolation) — used for the combined-balance view.

See the frontend's `src/db/sync.ts` for the client side of this contract.
